# Architecture.md: twep Architecture

## KISS / DRY

Architecture updates must follow KISS and DRY. Express boundaries, responsibilities, and trust decisions in the smallest practical units. When the same decision must be explained in multiple documents, designate one canonical source and have the others refer to it. Add an abstraction layer only after its necessity has been confirmed across multiple backends or multiple call paths.

## Overview

twep has plain Linux and TrustZone (OP-TEE) backends behind the same public C
ABI. Both execute the same TEEP Agent and Trusted Wasm App binaries.

```text
User
  |
  v
twep-cli(Go)
  |
  | Unix domain socket + CBOR
  v
twepd(Go daemon)
  |
  | cgo + C ABI
  v
twep-wr public C ABI
  |
  +-- plain Linux backend
  |     `-- REE WAMR
  |           +-- TEEP_Agent Trusted Wasm App
  |           `-- general Trusted Wasm App
  |
  `-- TrustZone backend
        `-- libteec / OP-TEE Client API
              `-- twep-wr TA
                    `-- TA-local WAMR
                          +-- TEEP_Agent Trusted Wasm App
                          `-- general Trusted Wasm App

TEEP_Agent host I/O
  +-- Catalog and app byte transport
  +-- AttesTAM HTTP transport through the REE broker
  `-- platform storage and Evidence services
```

## Confirmed Architecture Decisions

- Resolver modes are selected explicitly: `mock`, `attestam-insecure`, or `attestam-verified`.
- Verified provisioning requires TEEP/COSE/SUIT verification against a real AttesTAM instance.
- Trusted Wasm Apps use a custom CBOR input/CBOR output ABI. `docs/ABI.md` is the canonical ABI specification.
- TEEP_Agent is a special Wasm App that can use the file/http/evidence/read-protected/random/time/log hostcalls. COSE_Sign1 generation for TEEP messages is performed inside the Rust TEEP_Agent.
- The TEEP_Agent Wasm Application and general Trusted Wasm Applications run as the same Wasm binaries regardless of whether the platform backend is Linux, TrustZone, SGX, or Keystone. No platform-specific Wasm artifacts are created. Platform differences are absorbed by hostcall implementations, the C ABI/TA commands, protected storage, Evidence generation, and runtime policy.
- `negaposi` supports JPEG input and output.
- `twepd` runs as a user service in the REE for both primary backends.

## Boundary Design

### Boundary Between twep-cli and twepd

- Communication: Unix domain socket
- Payload: CBOR
- Connection unit: one request/one response
- The default socket directory is `0700`, and the socket file is set to `0600` after listen. For a custom socket path, validate the owner and mode of the parent directory.
- twep-cli does not directly manage the daemon lifecycle. However, helper commands such as `twep-cli daemon status` may be added for development.
- twepd may process multiple requests sequentially or concurrently. The current configuration processes one request at a time for safety.

### Boundary Between twepd and twep-wr.so

- Communication: C ABI calls from cgo
- Payload: CBOR byte sequences and configuration values
- The Go side does not retain internal pointers to WAMR or Wasm memory.
- A buffer returned by the C side must always be released with the C-side free function.
- The ABI is versioned. It provides `twep_wr_get_abi_version()`.

### Boundary Between twep-wr.so and Wasm Apps

- Communication: Wasm export function calls
- Payload: CBOR byte sequences
- Memory management: the app allocates, the host copies, and the app frees.
- Separate hostcalls for TEEP_Agent from those for general apps.
- General apps currently receive no hostcalls. Logging is only a future
  allowlist candidate and is not registered for a general-app runtime.

### Boundary Between TEEP_Agent and AttesTAM

- Communication: TEEP-over-HTTP
- Example endpoint: `http://127.0.0.1:8080/tam`
- Payload: TEEP messages (CBOR/COSE) in `attestam-verified` mode
- Even in `attestam-insecure`, follow the AttesTAM payload specification: the initial POST has an empty body, and the response body is treated as a COSE-wrapped TEEP message (CBOR). At the current stage, TEEP_Agent extracts the COSE_Sign1 payload and determines that the TEEP message type is QueryRequest. It then generates a `twep-app-v1` SUIT Component Identifier from the target command and creates the QueryResponse payload. In the insecure development demo, HTTP POST is delegated to the REE-side Go module `internal/teepbroker`, which is treated as `TEEP_Broker`, while the QueryResponse/Success COSE_Sign1 signatures are generated by the development ESP256 signer inside the Rust TEEP_Agent. For an Update, diagnostic `teep-agent/update-*` observations may be written before validation. A mismatched or unsupported component is rejected before staging, Success, or installation. A matching supported payload proceeds through SHA-256 verification and staging, then Success and installation. A matching `twep-app-v1` payload is promoted to `apps/<command>.wasm` and, only in `attestam-insecure`, generates a development Catalog File with source `attestam-insecure`. Final verified mode requires a separately verified `twep-catalog-v1` Catalog TC for Catalog updates.
- The formal responsibilities of the Go/REE side are TEEP_Broker operations such as IPC with `twep-cli`, HTTP/TLS communication, buffer transport, and state file I/O. Generation and verification of COSE data, generation and verification of TEEP protocol messages, Evidence generation, SUIT manifest processing, Wasm App verification, Catalog lookup, and Catalog/app promotion decisions are the responsibilities of TEEP_Agent inside the TEE. QueryResponse/Success COSE_Sign1 generation has already moved to the Rust TEEP_Agent, and the verification API in `internal/verifiedteep` remains as an intermediate implementation for development fixtures and parser tests. The `coset` crate is the first choice for the Rust-side COSE implementation.
- For Remote Attestation runtime communication, the twep-side TEEP_Agent/TEEP_Broker sends TEEP-over-HTTP to AttesTAM, and AttesTAM forwards Evidence to the Veraison Verifier. The user state directory stores the Catalog, app cache, TEEP_Agent observation artifacts, and development fixtures; it does not communicate directly with Veraison in the normal execution path.
- AttesTAM is the Relying Party for the Verifier result and does not forward the EAR body to TEEP_Agent. TEEP_Agent may establish AttesTAM acceptance only from a TAM-signed Update that it verifies in the live Evidence challenge-response session. A later component session may reuse that protected acceptance only while its generation remains current and the later signed Update is bound to fresh session tokens and its exact preceding QueryResponse. This is an AttesTAM-specific derived result. HTTP `204 No Content` is an unsigned session outcome and is never grounds for AttesTAM acceptance or the compatibility `evidence-affirming` state.
- Under D043, the pending Evidence transcript belongs to a real TA session context and is never recovered after session close or restart. This tranche permits exactly one sequence-bearing manifest per Update. After complete Rust TEEP_Agent verification, a dedicated TA command advances the consumed QueryResponse digest and component sequence together in a two-slot, crash-recoverable logical `teep-acceptance-state.cbor` record; the generic secure-storage PUT is not used. A positive AttesTAM acceptance result is usable only when its `acceptance_generation` matches the current acceptance state, so a crash between consumption and result persistence fails closed.
- The `mock` resolver installs local development fixtures and makes no security claim.
- The `attestam-insecure` resolver provides explicitly insecure AttesTAM integration testing.
- The `attestam-verified` resolver applies the documented COSE signature, SUIT manifest, acceptance freshness, and replay checks against a real AttesTAM instance. Fixed development credentials keep repository demonstrations at `final-verified=false`.

## Runtime Configuration

### WAMR Instance Separation

`twep-wr.so` separates at least the following two types of WAMR execution context.

| instance | purpose | hostcall |
| --- | --- | --- |
| teep-agent-runtime | Catalog retrieval and preparation for Trusted Wasm App install/update/load | file/http/evidence/read-protected/random/time/log in `twep_teep_env` |
| app-runtime | Trusted Wasm App executed as a user command | None |

Reasons:

- TEEP_Agent requires administrative privileges, but equivalent privileges must not be granted to general apps.
- The same privilege separation is enforced by the REE runtime in the Linux backend and by TA-local WAMR in the TrustZone backend.
- Per-app resource limits are easier to configure.

The import module for TEEP_Agent hostcalls is `twep_teep_env`. Because the general app runtime is not configured with TEEP_Agent capabilities, imports of the legacy `env` hostcalls fail as unresolved calls, and imports of `twep_teep_env` are rejected at the hostcall entry point. If logging or similar capabilities are allowed for general apps in the future, introduce them through a namespace separate from TEEP_Agent and a Catalog allowlist.

### Resource Limits

Default configured limits:

| item | default |
| --- | --- |
| wasm stack | 64KiB |
| wasm heap | 1MiB to 16MiB; may be overridden per app in the catalog |
| output CBOR size | 16MiB |
| execution timeout | 5 seconds |
| concurrent execution | 1 |

Because `negaposi` performs JPEG decoding and encoding inside Wasm, it may require a larger heap. Allow individual settings through `resource_limits` in the catalog.

## Data Flow

### CLI Request Generation

1. `twep-cli` obtains the command name and raw argv.
2. `cliargs` lightly parses the raw argv.
3. `argv` stores the original tokens.
4. `inferred_params` stores inferred values such as integers and booleans.
5. If `--cbor-file` or `--cbor-hex` is specified, the app input CBOR is stored directly in `app_input`.
6. The entire request is encoded as canonical CBOR.

When `app_input` is specified, twepd passes those bytes directly to the Trusted Wasm App. When it is not specified, twepd constructs `app-input` CBOR containing only `schema_version`, `command`, `argv`, `inferred_params`, and optional `stdin/files/metadata`; `request_id`, `cwd`, and `options` are not included in general app input.

### twepd Processing

1. Read a frame from the UDS.
2. Decode the CBOR request.
3. Validate the request size, schema_version, command name, and path.
4. Normalize the command, app input CBOR, and request timeout, then call `twep_wr_execute`.
5. Wrap the result CBOR in the response.
6. Return it to twep-cli.

### twep-wr Processing

The Linux backend performs the following operations in `libtwep_wr.so` within the REE process.

1. Initialize WAMR during `twep_wr_init`.
2. Prepare the TEEP_Agent runtime during `twep_wr_execute`.
3. Pass a `resolve_app` request to TEEP_Agent.
4. TEEP_Agent performs catalog lookup, catalog entry validation, and app file SHA-256 verification.
5. If necessary, retrieve the catalog/app through the configured mock or AttesTAM resolver mode.
6. TEEP_Agent returns the app file path, expected hash, and resource limits.
7. twep-wr reads the file and defensively verifies SHA-256 again immediately before loading.
8. Load the Wasm into app-runtime.
9. Pass the app input CBOR to `twep_app_main`.
10. Return the app output CBOR to Go.

The TrustZone backend preserves public C ABI v3, establishes a TA session in `twep_wr_init`, and marshals `twep_wr_execute` into TA private commands. The production path uses `TA_TWEP_WR_CMD_INIT`, `TA_TWEP_WR_CMD_EXECUTE`, and `TA_TWEP_WR_CMD_RESUME_HOST_IO`, and executes TEEP_Agent and general apps in the WAMR runtime inside the TA. The formal responsibilities of the REE side are limited to TEEC transport, transport of state/cache object bytes, actual HTTP communication, the Evidence bytes broker, and CLI file I/O.

The production runtime inside the TrustZone TA performs the app ABI version check, applies Catalog resource limits, executes `twep_app_main`, calls `twep_app_free`, wraps app output CBOR, and cleans up after each execution. In the verified path it loads the one active protected app and requires its stored digest to match the digest in the TEEP Agent's Catalog resolution result immediately before WAMR load. Because general apps are not configured with TEEP_Agent hostcall capabilities, general apps that import `env.*` or `twep_teep_env.*` are rejected.

In accordance with D027, continuation of host I/O for TEEP_Agent inside the TrustZone TA does not retain a WAMR call frame during an REE round trip. The TA retains `request_id`, the TEEP_Agent command, normalized input, resolver/session policy, hostcall kind, `io_id`, request bytes, and a transcript digest or sequence as session-local continuation state, then returns `need_host_io`. On `RESUME_HOST_IO`, the TA validates the host I/O result and re-executes the same TEEP_Agent Wasm binary or invokes an explicit continuation entry. The bytes returned from the REE are hostcall result material and do not make the REE the authority for Catalog resolution or promotion decisions.

SHA-256 usage in the TrustZone path is divided by responsibility. The platform-independent TEEP_Agent Wasm owns the Catalog/SUIT trust decision and authorizes an app only when the verified payload digest equals the protected Catalog entry. TA C hashes bind private-command transcripts and protected commit records: it verifies that committed bytes match the supplied digest and later compares the stored digest with the resolver result before execution. TA C does not select Catalog entries, classify Trusted Components, or make promotion policy from a digest.

## Catalog Resolution

Catalog entries use command names as keys. Each entry contains at least:

- command name
- component id
- version
- wasm file name
- sha256
- ABI version
- resource limits
- optional args schema

TEEP_Agent owns the Catalog File and performs both lookup and hash verification. twepd and debug tools may refer to it read-only. The Linux backend's twep-wr.so may verify the same hash again to detect races before WAMR load, but it is not the authority for Catalog resolution. In the TrustZone backend, TEEP_Agent inside the TA performs Catalog lookup, TC/app classification, payload hash verification, and promotion decisions, while the REE side is responsible only for transporting cache bytes for the Catalog, apps, and TEEP_Agent artifacts.

In the verified academic path, the Catalog File itself is an independent SUIT Trusted Component verified by TEEP_Agent. The SUIT Component Identifier for the Catalog TC is `[ bstr("twep-catalog-v1"), bstr(catalog-name) ]`, with `default` as the accepted catalog name. A `twep-app-v1` app TC cannot modify the Catalog. TrustZone stores one active app in TA-owned two-slot protected state; the `apps/<command>.wasm` name is a TEEP Agent hostcall view of those protected bytes, not an REE cache file.

TEEP_Agent Wasm is bundled as a repository build artifact. The Linux backend installs it into the state directory and verifies its demo code-signing identity. The TrustZone backend measures the exact TEEP_Agent Wasm bytes loaded inside the TA and compares them with protected identity state. Because TEEP_Agent verifies the Catalog File and Trusted Wasm Apps, this repository does not update TEEP_Agent itself through the same AttesTAM session.

## TEEP Design

### Resolver Modes

Configuration explicitly specifies the resolver mode.

```toml
[resolver]
mode = "mock" # "mock" / "attestam-insecure" / "attestam-verified"

[attestam]
url = "http://127.0.0.1:8080/tam"
insecure_demo_mode = false
connect_timeout_ms = 3000
request_timeout_ms = 10000
```

- `mock`: Installs local development and test fixtures from `testdata`.
- `attestam-insecure`: For development. Prioritizes connectivity with AttesTAM and explicitly indicates the unverified state.
- `attestam-verified`: The D045 PoC protocol-validation route. It requires TEEP/COSE/SUIT verification, but the fixed development signers and REE-produced development Evidence are explicitly insecure and cannot establish `final-verified=true`.

### Mock Resolver

The mock resolver performs the following:

- In `mock` and `attestam-insecure`, if there is no local catalog, a development catalog may be copied into state.
- In `mock` and `attestam-insecure`, if there is no app wasm, it may be copied into state from a development Wasm artifact.
- In `attestam-verified`, do not perform development catalog seeding, `TWEP_CATALOG_CBOR` overrides, mock app installation, or insecure Catalog/app promotion. Linux performs verified dry-run observation. The completed M9.1 TrustZone path executes the D045 live challenge-response, verifies the immediate TAM-signed Update, consumes exactly one current D043 acceptance generation, and then stops with `teep.verified_required` without Catalog/app installation, Success, promotion, or app execution.
- D047 authorizes the M9.2 TrustZone path to commit only the exact default Catalog TC through a dedicated TEEP_Agent-only protected transaction. Rust owns Catalog semantics; TA C writes and verifies an inactive protected slot and activates it only through the matching D043 component sequence. It sends Success only after commit/readback, never executes an app during M9.2, and remains explicitly insecure with `final-verified=false`. It must not reuse `attestam-insecure` promotion behavior.
- The default M9.3 TrustZone path obtains the requested app TC after the protected Catalog exists. Rust requires its command and digest to match that Catalog, then asks the TA to publish one active protected app through a separate two-slot/D043 transaction. The TA reloads those bytes and checks their stored digest against Rust's resolver result immediately before WAMR execution. Later invocations can reuse the protected Catalog and app without a TAM connection; fixed development credentials still require `final-verified=false`.
- Calculate the hash and compare it with the catalog.

### AttesTAM Connection

`attestam-insecure` is used only as an explicit development mode. `attestam-verified` does not permit incomplete TEEP/COSE/SUIT/attestation bypasses.

### Verified TEEP Requirements

- Generate QueryRequest.
- Return agent Evidence and the list of installed TCs in QueryResponse.
- Receive the SUIT manifest and TC binary in Update.
- Return the result in Success/Error.
- Make successful retrieval of the Catalog File as a `twep-catalog-v1` Catalog TC and Trusted Wasm Apps as `twep-app-v1` app TCs in verified mode with a real AttesTAM instance a final acceptance condition.
- If the AttesTAM side integrates with a Verifier, handle agent key binding and freshness.

## File System Policy

### State Directory

Allow writes only under `$STATE`.

```text
$STATE/
├── catalog/
│   ├── catalog.cbor
│   └── catalog.dev.json
├── apps/
│   ├── helloworld.wasm
│   ├── calcadd.wasm
│   └── negaposi.wasm
├── components/
│   ├── hello.txt
│   ├── install-metadata.cbor
│   └── install-status.txt
├── teep-agent/
├── tmp/
└── locks/
```

### Path Constraints

- Only a basename is allowed for `wasm_file` in the catalog.
- Prohibit `/`, `..`, and NUL bytes.
- During installation, write to a temporary file and perform an atomic rename after hash verification.
- When updating an existing file, verify its version and hash.

## Error Model

Errors across twep are classified into the following layers.

| code | meaning |
| --- | --- |
| `cli.usage` | Invalid CLI arguments |
| `ipc.connect` | Unable to connect to twepd |
| `ipc.protocol` | Invalid frame/CBOR |
| `daemon.request` | twepd request validation failed |
| `catalog.not_found` | The command name does not exist in the catalog |
| `catalog.invalid` | Corrupt catalog or invalid schema |
| `app.missing` | Wasm app is not installed |
| `app.hash_mismatch` | Hash verification failed |
| `app.abi` | App ABI mismatch |
| `app.runtime` | WAMR execution failed |
| `teep.network` | AttesTAM connection failed |
| `teep.protocol` | Invalid TEEP message |
| `teep.attestation_unsupported` | The AttesTAM QueryRequest requested Evidence, but the current platform does not support it |
| `teep.verified_required` | An unverified TEEP/COSE/SUIT path became necessary in verified mode |
| `security.insecure_mode_disabled` | Insecure processing is disabled |

## Logging

- twep-cli: Emit concise messages to stderr. Use `--verbose` for details.
- twepd: Emit structured logs to stdout/the systemd journal.
- twep-wr.so: Write C-side runtime diagnostics directly to stderr. The public C
  ABI does not expose a logging callback.
- TEEP_Agent: Log through the `twep_host_log` hostcall, which currently writes
  to stderr.
- Do not log secrets, tokens, keys, or binary bodies.

## Architecture Notes for Future TEE Migration

- The C ABI of `twep-wr.so` becomes the boundary for TEE ports.
- Separate platform-dependent processing into `lib/twep-wr/src/platform/<backend>/`. The initial backends are `linux`, `trustzone`, `sgx`, and `keystone`.
- `platform/linux` is an REE-only development backend. Even if it provides a sealed-storage-like API, it must not be used for final verified security claims. In internal `twep-wr` platform metadata, treat the sealed storage security of this backend as `observation-only`.
- Move `platform/trustzone` from the OP-TEE scaffold toward the production runtime. Do not pass REE state file I/O into the TA as arbitrary paths; treat it as byte transport for TA-managed object ids. Connect to the TA in `optee/twep-wr-ta/` through TEEC and handle REE FS Secure Storage write/read, trusted random/time, production WAMR execution, and TEEP_Agent hostcall resume. This repository adopts OP-TEE REE FS Secure Storage as the formal TrustZone secure storage policy and permanently configures `CFG_REE_FS=y` and `CFG_RPMB_FS=n`. Because rollback attacks are outside the threat model, `sealed-storage-security=tee-ree-fs-secure-storage` may be used in final verified mode, while `sealed-storage-rollback-protected=false` remains diagnostic information.
- For `platform/sgx` and `platform/keystone`, reserve only the backend boundaries and return `unsupported` for protected storage until it is mapped to platform-specific sealed storage.
- For OP-TEE/TrustZone, move the implementation of `twep_wr_execute` into the production WAMR runtime inside the TA, and map secure storage, trusted time/random, and the Evidence token generation broker to `platform/trustzone`. Retain `TA_TWEP_WR_CMD_WAMR_SPIKE_EXEC` for regression testing, but it is not the target path for the production app runtime, TEEP_Agent, Catalog resolution, `calcadd`, or `negaposi`.
- For SGX, convert the equivalent of twep-wr.so into Enclave.so, and map sealed blobs, DCAP Quote, and in-enclave freshness management to `platform/sgx`.
- For Keystone, map the equivalent of Keystone enclave sealed storage, attestation reports, and freshness management to `platform/keystone`.
- The Go-side twepd takes on a role similar to a TEE Broker/REE component.
- Because TEEP_Agent is implemented in Wasm, its management logic may be reusable on runtimes inside TEEs.
